# AI Development Log — Picture Battleship: Grid Hunter

## Tools Used

- **Claude Code (Sonnet 5, Anthropic)** — used as an AI pair-programming assistant to scaffold and implement the game, iterating from an initial desktop-app version, to a single-board browser version, to the current two-board Battleship-style redesign linked on the portfolio.

## Key Prompts

1. **Initial build prompt** — Requested a `tkinter`-based Python desktop app for a 2-player local "Picture Battleship" game using the keyless Picsum Photos API: a 4x4 hidden image grid, three ammo types (Grayscale Recon, Blur Radar, Direct Precision Hit), a guess phase with 4 candidate thumbnails, round-based scoring, and academic deliverables (`.gitignore`, `requirements.txt`, `README.md`, `prompt_log.md`).
2. **Pivot prompt** — "actually do NOT use tkinter... create this game in a page linked on my agongster.github.io portfolio... matching the theme of my home portfolio page." This replaced the desktop app entirely with a static HTML/CSS/JS page under `picsum-battleship/`, reusing the portfolio's existing color tokens, fonts, and dark/light toggle from `../styles.css`.
3. **Difficulty-redesign prompt** — "this game is way too easy... it's very easy to recognize when the pictures are all quite different colors and shapes." Requested a ship-placement phase, an 8x8 grid, and having players choose the candidate images for each other ("display many images and have the player choose 8 of them for the other player to guess from"), plus "find other ways to make it potentially more difficult."
4. **Follow-up refinement prompt** — "try making the board 12x12... for the ships, just clicking the board for a given ship should change the orientation of the board... the player should be able to choose what image is the selected image... for the missed shots, the player should get a maximally blurry, grayscale part of the image [and] the whole time, keep the blurriness at max." Five distinct, independently shippable changes to the same architecture: a bigger grid, click-driven ship orientation instead of a toggle, builder-chosen targets instead of a system-assigned one, and replacing the ammo-selector mechanic with an automatic reveal system tied to ship status.
5. **Second follow-up prompt** — "when the user manages to select a ship successfully, leave it in grayscale, just a little sharper. Do not have rounds in the implementation... shaking effect when a ship is hit... celebratory effect [animating] the player that won... 12 random images... make it 20... when a player hits a ship, they should keep getting turns until they have a miss." Six more changes layered on the same two-board architecture: reversing the previous "sinking = color" decision, removing the round loop entirely (one setup + one playthrough per game), two new juice/feedback effects (shake, victory confetti), a bigger candidate pool, and a hit-streak turn rule.
6. **Ship-placement UX prompt** — "all ships are initially already placed randomly, and the user should drag to move the different ships. If they click on any of the ships it should change orientation. They should not be placing ships one at a time." Replaced the click-a-tray-item-then-click-a-cell placement flow with: fleet auto-placed the instant the step opens, drag to relocate a ship, plain click (no movement) to rotate it.
7. **Color prompt** — "make the ships different colors." Gave each of the 4 fleet ships (Cruiser, Frigate, Submarine, Scout) its own color, used consistently for that ship's cells on the placement board, its drag preview, and a matching swatch in the tray legend.
8. **Fleet-size prompt** — "there should be a few more ships, one more 3-tile one and one more 2-tile one." Added Destroyer (length 3) and Corvette (length 2) to `SHIP_FLEET`, bringing the fleet to 6 ships / 13 total cells on the 144-cell board. Since every placement/rendering function already iterates `SHIP_FLEET` generically rather than assuming a fixed count of 4, this was purely additive — no logic changes, just two new entries (with two more distinct colors) and updated fleet-composition text in the UI copy and docs.

## Design Decisions for the Difficulty Redesign

The redesign prompt described a real Battleship-style mechanic on top of a game that, until then, had one *shared* board both players fired on — which doesn't map cleanly onto "each player secretly places ships" or "one player curates the other's decoys" without someone being able to see the answer before guessing it themselves. Rather than guess at the intended turn structure for a rewrite this size, I used `AskUserQuestion` at two points: once to pin down what should happen when a shot lands on an enemy ship, whether ship placement persists for the whole game or resets each round, and how curator/solver fairness should work; and again to confirm a concrete two-board turn-structure interpretation ("each player always fires on their own board, built by their opponent") before implementing it. Both were substantial, hard-to-reverse-cheaply architecture calls, so confirming them up front was cheaper than rewriting the whole state machine twice.

Resulting architecture: each round now has **two independent boards** — `boards[i]` is solved by player `i` but *built* by player `(1 - i)`, who picks that board's 8 candidate photos (from a 12-photo pool, real target already locked in) and places a 4-ship fleet (lengths 3/2/2/1) on it. Ships are re-placed fresh every round. Landing a shot on an opponent-placed ship penalizes the ship's *owner* (the builder), not the shooter — confirmed via `AskUserQuestion` as the preferred design, since it keeps ship placement a real defensive trade-off (spread them out or risk losing points) rather than a bonus-hunting exercise for the shooter. Turns alternate between the two players' boards; once a board is solved (or fully revealed with no correct guess) that player sits out while the other continues solo, and the round only advances once both boards are resolved.

## Design Decisions for the Follow-Up Refinement

Two of the five requests in the follow-up prompt were unambiguous find-and-replace-scale changes (`GRID_SIZE = 8 → 12`; deleting the target-star-is-automatic logic in favor of a click-to-choose flow). The other three needed real design calls:

- **"Clicking the board... should change the orientation"** replaced the Horizontal/Vertical toggle buttons entirely. The rule I landed on: clicking an empty cell while a ship is armed places it (default horizontal); clicking that *same* ship's own cells again rotates it in place around its first cell; clicking a different empty cell moves it (keeping its current orientation). Ship tray items stay clickable after placement (previously they disabled once placed) so a player can re-arm a ship to move or rotate it later in the same setup step.
- **"The player should be able to choose what image is the selected image"** meant fetching the full-resolution target image *after* the builder picks it, not before — preloading all 12 pool photos at full size (900–1000px) just to throw away 11 of them would be wasteful. `chooseTarget(index)` sets a `null` (loading) state, re-renders immediately so the UI shows a spinner-ish dimmed star, then resolves the preload and re-renders again. The Next button stays disabled until that resolves, and clicking the target thumbnail again unsets it entirely (clearing `targetId`/`targetOk`) so a builder can change their mind before committing.
- **The three-tier reveal system** ("missed shots... maximally blurry grayscale," "shots on a ship... a little less blurry," "once fully shot, add color," "keep the blurriness at max the whole time") reconciles as: two blur levels, not three — misses stay at max blur forever, and *any* ship-cell hit (sunk or not) drops to a slightly-less-but-still-quite-blurry level and never goes lower, even once sunk. The only thing sinking a ship changes is grayscale → color. This satisfies "keep the blurriness at max" as "never reaches true clarity" rather than a literal constant, since the middle sentence explicitly asks for *less* blur on a hit — the two would otherwise contradict each other. This entirely removed the ammo-selector mechanic (Grayscale Recon / Blur Radar / Direct Precision Hit): there's no longer a player choice at all, since the tile's treatment is fully determined by ship state.

The reveal tiers are computed live from ship data on every render (`tileVisualTier(board, row, col)`) rather than stored per-tile at reveal time, which is what makes "once the ship is fully shot, add color" apply retroactively to that ship's *earlier* hits too, not just the shot that sank it — confirmed visually in testing (see below).

## Design Decisions for the Second Follow-Up

- **"Leave it in grayscale, just a little sharper" directly reverses the previous round's "add color" decision** for a sunk ship — the CSS class stayed `tier-sunk`, only its `filter` changed, from `blur(2.5px)` with color to `grayscale(1) blur(1px)`. This is a good example of a design call from one session not being permanent: the user tried the color-reveal version, decided against it, and asked for something adjacent instead (sharper-but-still-gray) rather than reverting to the pre-redesign ammo system entirely.
- **"Do not have rounds"** could have meant several things (unlimited rounds, a fixed different count, or literally one pass). Given the surrounding context — this is a refinement of an already-shipped feature the user has presumably played — I read it as the simplest literal instruction: delete the round concept entirely, so the game is one setup phase followed by one playthrough to a single game-over. `advanceRoundOrEndGame()` (which incremented `state.round` and re-ran setup) collapsed into a direct `endGame()` call once both boards resolve, and `state.round`/`MAX_ROUNDS`/the "Round X of Y" label were deleted rather than hidden, per "not have rounds in the implementation" (not just "don't show rounds").
- **The hit-streak rule ("keep getting turns until they have a miss") had to interact with the existing Guess/Pass decision** rather than replace it. Rule: a wrong guess always ends the turn, even mid-streak (guessing wrong has to cost something, or a hit-streak plus free wrong guesses would have no real risk); a miss always ends the turn; anything else (hit, or a correct guess that doesn't end the game) lets the same player continue. This collapsed `finishTurn()`/`advanceRoundOrEndGame()` into one `resolveAfterShot(switchPlayer)` helper so the board-exhaustion and both-boards-resolved checks aren't duplicated between the "same player continues" and "switch to opponent" paths. The Pass Turn button's label now dynamically reads "Fire Again" after a hit so the state isn't hidden from the player.
- **Confetti needed a real z-index fix, not a guess.** The natural DOM structure (a `.confetti-layer` div as a sibling *before* `.modal-card`, both inside the fixed overlay) relies on paint order for stacking, but `.confetti-layer` had an explicit `z-index: 1` for its own reasons (to sit above the darkened backdrop) — which put it *above* `.modal-card` too, since an unpositioned/default-stacking sibling loses to any sibling with a set `z-index`. Fixed by also giving `.modal-card` `position: relative; z-index: 2`, not by removing the layer's z-index (it still needs to be above the backdrop it's not a descendant of, conceptually — being explicit on both sides is clearer than relying on DOM-order stacking that would break the moment either element's CSS changes).

## Design Decisions for the Ship-Placement UX Change

The previous placement flow (arm a ship from a tray, click a cell to place it, click again to rotate or move) was a reasonable design for "the player builds up a layout from nothing," but the new prompt explicitly rejects that premise — "they should not be placing ships one at a time." That's a different starting condition (a complete random layout you *edit*, not an empty board you *fill*), so this wasn't a small tweak to the existing click handler; the whole interaction model changed from "click to place, click to modify" to "everything's already placed, drag or click to modify":

- **Ships are placed once, at `startBuilderPhase()` time**, via a `randomFleetPlacement()` helper extracted from the old auto-place button handler. There is no "unplaced" state anymore — `state.setupArmedShipId` (which ship is selected for the next click) was deleted entirely, since there's no longer a concept of an unselected/unarmed ship waiting to be placed.
- **Distinguishing a click from a drag** needed real pointer tracking, not just a `click` listener: `pointerdown` on a ship cell records the ship and starting cell; `pointermove` (attached to `window` for the duration of the drag, so the cursor can leave the grid without losing the drag) recomputes the ship's candidate position by translating all its cells by the delta from the start cell, live-previewing it as valid (normal ship color) or invalid (red) without committing; `pointerup` commits the move if the pointer ever moved to a different cell, or — if it never moved at all — treats the whole gesture as a click and rotates the ship in place instead. This is why a single interaction had to fork into two different outcomes (move vs. rotate) based on one boolean (`moved`), not two separate handlers.
- **The ship tray lost its interactivity, not its purpose.** With no "arm this ship" step, tray items stopped being buttons — they're now a plain legend (name + a `■` bar showing length) so players can still tell Cruiser from Frigate at a glance, but clicking them does nothing, since the board itself is now the only interaction surface. The two setup buttons collapsed from three (Auto-place, Reset, Confirm) to two (Shuffle, Confirm): "Reset" doesn't have a meaningful target state anymore (there's no empty layout to reset *to*), so it was dropped rather than repurposed.

## Technical Insights

- **Keyless API, no proxy needed**: `https://picsum.photos/v2/list` and `https://picsum.photos/id/{id}/{w}/{h}` both send `Access-Control-Allow-Origin: *`, so the game can call Picsum directly from client-side `fetch()`/`Image()` with no backend or API key — confirmed by inspecting response headers with `curl -H "Origin: ..."` before committing to the client-only architecture.
- **CSS does the image slicing**: instead of a canvas or an image library, each of the 16 tiles is a `<button>` with the *same* full-image URL as its `background-image`, sized to `400% 400%` and offset with `background-position` percentages (`col/3 * 100%`, `row/3 * 100%`). The browser fetches the image once and reuses it from cache for all 16 tiles.
- **Ammo effects are CSS filters, not pixel manipulation**: `filter: grayscale(1)` and `filter: blur(6px)` applied per-tile give the same effect Pillow's `ImageOps.grayscale`/`ImageFilter.GaussianBlur` gave in the original Python version, with zero image-processing code.
- **Robustness without try/except**: every image URL is preloaded with a `new Image()` + `onload`/`onerror`/timeout race before being used, so a failed or slow Picsum request degrades to a placeholder tile or thumbnail instead of leaving a broken image icon or crashing the game loop.
- **Theme reuse over duplication**: the game page links the portfolio's own `styles.css` (for CSS variables, fonts, header layout) alongside a small page-specific `style.css`, and re-implements just the ~10-line theme-toggle script rather than including the full `scripts.js` (which has home-page-only features like the flower-click effect and reveal-on-scroll animations that assume elements this page doesn't have).
- **Testing caught a real bug**: initial manual review looked fine, but driving the page with a headless Chromium (Playwright) end-to-end — reveal a tile, open the guess panel, guess correctly/incorrectly, run all 4 rounds, hit the victory modal, toggle themes — surfaced no console/JS errors and confirmed scoring (`100 - 5×revealed`), turn-passing, and round advancement all matched the intended rules before calling the feature done.
- **Re-reading my own code caught bugs a first pass missed**: a second read-through of the redesign (before running any tests) found a scoreboard-highlight bug where a stale, always-`undefined` `state.setupPhaseActive` check made a player badge glow during setup/builder phases when it shouldn't, and an orientation-toggle button that didn't visually reset between the two builders' ship-placement steps even though the underlying state did. Both were fixed before testing rather than after, since they were easy to reason about statically without needing a browser.
- **Testing the ship-hit mechanic needed a targeted script, not just a full playthrough**: a full 4-round Playwright run (auto-pick decoys, auto-place ships, reveal-one-tile-then-guess-correctly each turn) finished cleanly with zero console errors, but with only one shot per turn there was roughly an 8/64 chance per shot of ever landing on a ship, and none happened to hit in that run. A second, purpose-built script swept many tiles across both boards before guessing, and confirmed the hit messages, the sunk-ship message, and the score deltas all attributed correctly to the ship's *owner* — including across the two different boards, which is the part most likely to have an off-by-one player-index bug.
- **A large rewrite reintroduced a class of bug the earlier version didn't have**: rewriting `index.html`'s Step 1 markup to remove the now-unneeded `decoy-need-label` span (its count is folded into the dynamic hint text instead) left `game.js` still calling `el.decoyNeedLabel.textContent = ...` against a `document.getElementById` that now returned `null`. This didn't show up as a syntax error or in a quick read-through — it only surfaced as a thrown `TypeError` the first time that code path ran, which silently stopped the async `chooseTarget()` flow partway through and left the UI stuck showing "Loading the target image…" forever. Caught it by running a headless Chromium test with a `pageerror` listener attached (not just `console.error`) and a long enough `wait_for_function` timeout to distinguish "genuinely slow" from "never happening." After that, cross-checked every remaining `getElementById`/`querySelector` call in `game.js` against the actual IDs present in `index.html` with a quick two-line `comm` diff, rather than trusting a manual read.
- **Verifying "keep the blurriness at max" needed a screenshot, not just a status-message check**: the sweep-test script watched for the word "sunk" in the status banner and screenshotted that exact moment — it shows a row of uniform blurry-grayscale miss tiles next to two tan/orange tiles from a just-sunk submarine, confirming the color-without-clarity effect actually reads correctly to the eye and isn't just correct in the underlying CSS class names.
- **A "confetti not visible" result turned out to be a timing artifact, not a bug — verified by inspecting computed styles, not by guessing**: a screenshot taken 0.3s after the victory modal appeared showed zero visible confetti, even though `document.querySelectorAll('#confetti-layer .confetti-piece')` confirmed 36 pieces existed in the DOM. Rather than assume the CSS was broken, I read a piece's actual `getBoundingClientRect()` and computed `opacity`/`animation-delay` — it was sitting at `opacity: 0`, positioned above the viewport (`top: -10%` of the layer, i.e. off-screen), with a `0.38s` animation-delay that simply hadn't elapsed yet at the 0.3s mark. Re-screenshotting at 1.2s showed the pieces mid-fall in full color. This is a case where "reproduce with more logging before concluding it's broken" saved a wasted CSS rewrite.
- **Forcing a specific test outcome (a clear winner, not a tie) needed a deliberate wrong guess, not more attempts**: an early version of the winner/confetti test just replayed the same "always guess correctly on the first miss" strategy used elsewhere, which is symmetric between the two boards and reliably produces a tie by construction — no amount of re-running fixes a deterministic tie. Fixed by explicitly making Player 2's first guess wrong on purpose (a fixed, known-bad candidate index), which reliably produces an unequal score and let the winner-only code paths (the bounce animation, the confetti spawn) actually get exercised.
- **Testing drag interactions needs real input simulation, not synthetic DOM events**: dispatching a fake `MouseEvent`/`click` wouldn't exercise this feature at all, since the whole point is distinguishing a drag from a click via real `pointerdown`/`pointermove`/`pointerup` sequences and `document.elementFromPoint()` hit-testing. Playwright's `page.mouse.move()/.down()/.up()` drives the actual OS-level input pipeline (via CDP), which the browser translates into genuine pointer events — so a script that reads each ship cell's live bounding-box center, moves the mouse there, and drags it to another cell's center is testing the real code path, not a shortcut around it. This confirmed both outcomes in one run: a zero-movement press+release rotated a ship (`"Submarine rotated to vertical"`), and a multi-step drag moved one (`"Submarine moved"`), with before/after snapshots of every `.has-ship` cell confirming the board actually changed each time.
- **Ship colors caught a sloppy test assertion, not a code bug**: the first drag-color check queried `.placement-cell.has-ship` and grabbed whichever element came back first, which during an active drag preview is just "the first ship cell in DOM order" — not necessarily the one being dragged, since three other ships' cells still carry that same class. It looked like a real bug (drag started on the cyan Cruiser, preview cell nearby came back green) until re-checking by row/col coordinates of the actual drop target showed the color was correct all along. A reminder that a failing assertion in a multi-element page needs to name *which* element it means, especially once there's more than one thing sharing a class.
